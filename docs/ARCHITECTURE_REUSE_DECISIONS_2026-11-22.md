## MCP and semantics

The former P4 JSON-RPC/stdio/HTTP implementation has been replaced by the official MCP Python SDK candidate (`mcp==2.3.0`) for session negotiation, JSON-RPC, stdio, and Streamable HTTP. SDK calls are exercised against P4's realistic synthetic protocol peer over both transports. The adapter maps configured tools to logical contract `1.1.0`; the additive fields require source semantic/version receipts, approved relationship contract and per-source extract hashes. `products/p4/mcp_workflow.py` validates those responses, bounded read-only scope, row grain, key cardinality/equality, population, timestamp/lag bounds and audit evidence before normalizing and invoking `engine.analyze`. The full synthetic mock workflow has positive and adversarial cases, including actual D01–D05 dossier generation. Actual meanings, approvals, permissions, source identifiers, and relationships remain owned by the administrator-governed Fab Insight MCP; the shipped mock IDs and mappings are synthetic-only.

The SDK and exact transitive hashes are an **optional** offline MCP extra. The bundled wheelhouse is only macOS ARM64 / CPython 3.11; Windows, Linux, other Python versions, current vulnerability closure, license/security approval, actual target host, and company MCP compatibility are not established. Core scientific analysis remains Python standard library only. The exercised workflow is synthetic-only; a company semantic-map authoring, source permission review and target-host qualification are still explicit pending steps. P4's product UI consumes the host's JSON evidence envelope and does not duplicate a semantic service.

## Scientific engines and test/development infrastructure

P4 retains its deterministic engine and preserved held-out/refusal fixtures. Existing independent D01–D05 and OSS comparisons remain in their qualified scope; the SciPy, pyDOE3, scikit-optimize, and statsmodels comparisons are benchmark-only and do not become product dependencies. Reuse is accepted only where the fixed oracle demonstrates the improvement. The suite UI tests use the P1 React/toolchain as a test fixture; their versions and lock remain P1-owned.

D03 uncertainty reuse decision: the simple runtime-only Bonferroni rectangle uses independent-unit Student-t mean intervals and does not assume cross-setting or cross-objective independence. Its Cornish-Fisher critical approximation is bounded to 10–300 degrees of freedom and at most 40 candidate-setting/objective means, then compared against SciPy `t.ppf` as an independent oracle. A qualification-only alternative used SciPy's vectorized paired `bootstrap` API, preserving complete lot vectors across settings/objectives; it returned narrower envelopes but missed the family-wise coverage target in both normal and heavy-tailed challenges, so the product retains the conservative Bonferroni method and adds no SciPy runtime dependency. Outcome-based constraint exclusions and incompatible populations suppress family-wise dominance evidence.

D05 OSS reuse decision: reviewed the MIT-licensed R package [HonestDiD](https://cran.r-project.org/web/packages/HonestDiD/HonestDiD.pdf), which implements Rambachan–Roth robust inference for difference-in-differences and event-study designs. Its event-study methods operate on a vector of event-time estimates and their covariance; this P4 contract supplies a single pre/post group contrast and no event-time covariance matrix. Applying the package's method to the current input would therefore be unsupported. The package also adds an R/CVXR solver dependency closure not otherwise present in the offline Python runtime. No runtime dependency was added. P4 instead reports an algebraic sensitivity interval by expanding its Welch interval by a declared absolute differential-trend bound, checks unit equality, exposes the null tipping point, and labels the result conditional; this is not represented as an HonestDiD robust confidence interval. A future authorized multi-period event-study contract should be evaluated against HonestDiD directly.

D05 claim boundary: observational DiD outputs always retain `causal_claim=false`. The old numerical gate is reported as `conditional_assumptions_passed`; `conditional_interpretation_eligible` remains false with `PENDING_BOUND_SOURCE_QUALIFICATION` because the adapter cannot verify that a documented bound is scientifically adequate. An independent injected-confounder challenge demonstrates that an underbound can make an opposite-sign true effect look directionally robust; this is a recorded limitation, never a claimed pass.

D04 confirmation-power reuse decision: compared the known-SD normal sample-size baseline with SciPy's qualification-only central-t/noncentral-t power calculation on 54 fixed standardized-MDE/alpha/target-power combinations. The normal baseline was below target in all 54 cases (minimum achieved power 0.121). A runtime-only three-term Cornish-Fisher critical approximation, a normal power tail, and one extra pair met or exceeded the SciPy noncentral-t target in all 54 cases (minimum 0.8003; mean 1.83/max 8 pairs above exact minimum). This is a finite-grid result, not an exact-power guarantee; distributions, variance inputs and actual feasibility remain review assumptions. SciPy stays qualification-only; no new runtime dependency was justified.

Follow-up adversarial qualification found the finite-domain limit of that decision: a 165-case independent SciPy sweep produced eight underpowered proposals, concentrated at alpha below 0.01 and requested power above 0.90. The proposal now refuses outside alpha [0.01, 0.10] and target power [0.80, 0.90], and labels the displayed target as approximate. A 560-case central/noncentral-t oracle challenge (360 fixed grid points plus 200 seeded interior points) found no underpowered proposal; five representative out-of-domain requests refused with zero runs. This supports only the checked normal-theory grid and caller-provided SD/MDE assumptions; it is not a universal power guarantee. SciPy remains qualification-only and no runtime dependency was added.

D04 response-surface reuse decision: added a bounded face-centered central-composite builder (2–8 factors, approved min/max levels, at least two center replicates, no deletion of points intersecting forbidden regions). The official [pyDOE3 response-surface docs](https://pydoe3.readthedocs.io/en/latest/reference/response_surface/) expose `ccdesign(face="ccf")`; P4's generated geometry exactly matches the BSD-3 pyDOE3 CCF reference for 2–5 factors and has full rank for every quadratic term. A known 3-factor quadratic is recovered to floating-point precision on 125 held-out grid points; the 8-run full-factorial baseline cannot identify the 10 quadratic terms (rank 7). The [pyDOE3 repository](https://github.com/relf/pyDOE3) is archived and directs users to the consolidated PyDOE project; its generator remains a benchmark-only reference, and P4 does not add an OSS runtime tree for a small bounded design formula. This does not establish noisy-response power, feasibility, or higher-order accuracy.

The loopback HTTP server is retained as a synthetic integration fixture for engine jobs and cancellation, but no longer serves HTML and is not a deployable product backend. The retired standalone page is retained only as local legacy evidence and is excluded from the transfer bundle. The P4 production-facing interface remains the deterministic Python analysis function and CLI until the suite host is available.

P1 owns `suite-ui-module.v1` and `suite-chart.v1`; P4 contributes `products/p4/ui/P4Panel.tsx`. P1's extracted local directory has no Git metadata and no integrated suite host was available, so host compilation, route mounting, shared ECharts execution, authentication, and target OS remain `NOT_RUN`/pending. P4 must not change P1-owned contracts locally. The minimal company-side step remains explicit: supply approved semantics, source/relationship contracts, logical-tool mapping, permissions and read limits; run a read-only qualification under documented authorization; then independently review provenance and engineer results.

Public distribution remains unapproved pending source ownership, license, company-information exposure, dependency vulnerability, and security review. No public push or external publication follows from these local changes.
